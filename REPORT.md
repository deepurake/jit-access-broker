# Architecture decisions

## Summary

The broker is a request -> decision -> grant state machine over SQLite, with the decision made in three layers: a deterministic ACL ceiling that can deny, a deterministic junk gate and an AI triage step that can hand an insufficient reason back to its requester, and a router that lets the AI auto-approve exactly one case (high confidence, approve, no risk flag) and sends everything else to a human. Humans decide through a single-use magic link whose decision is a POST. Pending reviews time out and fail closed. Expiry is derived at read time and enforced on the external system by a sweeper. Races are settled by guarded SQL transitions. Any component that throws routes the request to a human rather than deciding it. The external grant is behind a two-method connector interface with an in-process mock and an HTTP mock that talks to a fake Okta sidecar, and Docker Compose runs the whole thing across process boundaries.

## Architecture

`Broker` (`broker/broker.py`) is the only class that knows the full lifecycle. It asks a `Policy` for a decision, asks a `ResourceConnector` to issue or revoke, asks a `Clock` for the time, and reads and writes through `Database`. Everything it depends on is an interface with at least two implementations, which is what made the pipeline buildable end to end with placeholders before any real policy existed and testable without sleeping or a network.

The seams:

- `Clock` (`SystemClock`, `FakeClock`): production code never calls `time.time()`. Tests move time forward instead of waiting.
- `Policy` (`AlwaysApprovePolicy`, `PolicyEngine`): one method, `decide(requester, resource, level, duration, reason) -> PolicyDecision`. `PolicyEngine` is the real one and is glue code, not a model call.
- `ResourceConnector` (`MockConnector`, `HttpResourceConnector`): `issue` and `revoke`. This is where a real Okta, AWS, or Workspace SDK call goes.
- `TriageProvider` (`MockTriageProvider`, `ClaudeTriageProvider`): the AI step. Returns a recommendation, a confidence, a risk flag, a justification, and the per-step results.
- `UserDirectory` (`DatabaseUserDirectory`): who has what role. Reads the `user_roles` table; in production a sync job from the IdP writes it.
- `RequesterHistory` (`RequesterHistoryReader`): a read-only projection over the same tables, answering "what does the broker already know about this person".
- `Database`: file-based SQLite, all writes, and the guarded transitions that make the state machine safe under concurrency.

## Decisions and why

1. **Policy is data: YAML authors it, a table serves it.** The ACL lives in `acl.yaml`, three roles and three rules, each a glob pattern plus a level and duration ceiling. A security person can read it, and a git diff of it is a policy change review. At runtime it is synced into an `acl_rules` table so the query path is indexed SQL and an audit row can reference a rule. That split is how Teleport roles, OPA bundles, and IAM policies already work, and I did not want to invent a different one. User-to-role is a table only, because it is operational data that changes with every hire and rotation and in reality is written by an IdP sync, not by hand.

2. **The ACL is a ceiling, triage is a judgment, and they are separate layers.** The ACL answers "may this role ever hold this level on this resource for this long". It is deterministic, and when it says no the AI never runs: no cost, and no possibility of the AI overriding a hard boundary. Triage answers the softer question, "does this reason justify this request, and is the scope proportionate", which is unstructured-text work that rules are bad at. Keeping them separate means the boundary stays auditable and the judgment stays swappable.

3. **Where AI helps and where trusting it is too risky.** The AI has two unilateral powers and no others. It can approve the obviously fine case (HIGH confidence, APPROVE, no risk flag), because a wrong auto-approve of a read on a permitted resource with a substantive reason is a low-cost mistake bounded by the ACL. And it can hand an obviously insufficient reason back to the requester (junk, or a reason that does not justify the permission asked for), because nobody gains anything by having their own request bounced back to themselves; even prompt injection in the reason field can only move the injector's own request, and only backwards. It cannot deny, and it cannot decide the ambiguous middle (over-scope, risk flag, low confidence), which goes to a human. This revises an earlier decision that a confident AI DENY should also go to a human. The concern behind that decision was that a wrong auto-deny wastes a human's time, but sending every "asdf" and every "I want to look at it" admin request to a reviewer wastes more, and the brief is explicit that approvers should not be an approval desk. The reasons to keep humans in the loop apply to approvals, not to denials, and a returned request is not even a denial: the requester resubmits or escalates.

4. **Return to requester and escalation.** A returned request has status `RETURNED`, which is terminal for the policy but not for the requester. Resubmitting with a better reason is a new request (a returned request is neither an active grant nor a pending review, so it is not a duplicate). Escalating turns it into a normal pending human review with the requester's note attached, audited as `ESCALATED` then `ROUTED_TO_HUMAN`; only the requester can escalate their own request, only a `RETURNED` one, once. The junk gate itself is deterministic code in the policy engine sharing its placeholder list with the mock triage step, so the two cannot drift, and it runs before any model call.

5. **Triage is multi-step, and least privilege is a suggestion, not an override.** Step 1 asks one narrow question, does this reason justify this permission, so that a "looks fine overall" impression cannot paper over a mismatch like a read-only reason for admin. Step 2 asks whether the level and duration are the minimum the reason needs, and if not, what would be. Step 3 gives the recommendation and confidence. The real provider makes two model calls (step 1 alone, then 2 and 3). I chose to surface the suggested minimum to the reviewer rather than silently grant less than was asked: a requester who gets `write` for an hour when they asked for `admin` for two will not know why their task failed, and a reviewer who sees "AI suggests write/3600" can make that call with the requester's reason in front of them.

6. **A component that throws is a failure, not a decision.** Denying is a decision. Throwing is a failure. `PolicyEngine` catches exceptions from the directory, the ACL engine, and the triage provider and returns ROUTE_HUMAN with the error text in the reason, so the reviewer and the audit log both see what broke. If the ACL boundary itself could not be evaluated, triage is skipped as well, because an AI APPROVE that nothing gated must not exist. The request never crashes, never auto-denies, never auto-approves.

7. **Magic link mechanics.** A human-routed request gets a random single-use token; `GET /approve/<token>` renders the request, the AI justification, the suggested minimum, and the escalation note if any. The decision is a POST to a separate URL. GET on the decide URL is a 405. This is not a formality: mail clients and link scanners prefetch URLs, and an approval that happens on GET is an approval nobody made. The token is the only credential (no login), single-use is enforced by a guarded UPDATE, the requester cannot approve their own request (and the attempt does not consume the link), and the deadline is checked when the link is used, not only when a sweeper runs.

8. **The approver is asleep: time out and fail closed.** Pending reviews have a deadline, four hours by default. Past it the request is `TIMED_OUT` and auto-denied, by the sweeper or at click time, whichever comes first. Failing closed is the only defensible default for an access broker; the cost is that a legitimate request waits for a resubmission. What I did not build is escalation of a pending review to a second approver or a reminder before the deadline. The shape is clear: a `notify` seam with a first implementation that prints, and a sweeper rule that re-routes a review approaching its deadline to a fallback approver list. It is the most valuable thing missing.

9. **Races via guarded transitions.** Grant expiry and revocation are both `UPDATE grants SET status = ? WHERE id = ? AND status = 'ACTIVE'`. Approve, deny, and timeout on a pending review are the same pattern against `status = 'PENDING'`. Whoever commits first wins; the loser's UPDATE affects zero rows and the caller sees `False` and does nothing, so an expired grant is never flipped to REVOKED, a revoked one is never re-expired, a decided review is never timed out, and two reviewers racing the same link cannot both win. The connector is only called by the winner, so the external system is told once.

10. **Duplicates.** A request for the same (requester, resource, access level) while a grant is active or a review is pending is recorded (the audit log captures every ask) and rejected pointing at the existing one. This runs before the policy, so a duplicate never costs a model call and cannot reach a different answer than the original. Duration and reason are deliberately not part of the key; it is the same access.

11. **Introspection, not stateless certificates.** The protected test service asks the sidecar whether the bearer token is still active on every request. Teleport does the opposite: short-lived signed certificates verified locally, with revocation handled by short TTLs and a synced lock list, trading immediate revocation for scale. The brief says a revoked or expired grant is no longer active, full stop, so synchronous introspection is the right choice here and the scaling cost is acknowledged.

12. **SQLite, file-based, never `:memory:`.** The broker keeps nothing important in memory. A restart re-derives everything from the tables and a reconcile pass at process start handles anything that expired or timed out while nothing was running. SQLite's single-writer model is also what makes the guarded transitions atomic without a separate lock. Tests run against real files in `tmp_path`, so the restart scenario is exercised for real.

13. **Process: TDD, and parallel subagents over a task DAG.** Stage 1 was a walking skeleton with placeholder policy and connector, proven end to end before any real logic. From then on each behaviour got a failing test first. The later stages were decomposed into a dependency table (`docs/superpowers/plans/`) and independent tasks were built in parallel by separate agents against shared contracts fixed up front (models, interfaces, schema). The tests are the executable spec; `tests/test_cli.py` in particular shows every command and its output. The design docs record the decisions and the deviations, including the one in decision 3.

## Edge cases from the brief

- **Approver never responds.** The review times out at its deadline and is auto-denied. The deadline is enforced by the sweeper and at click time. No escalation yet; see decision 8.
- **A grant expires mid-revoke.** Guarded transitions (decision 9). One of the two wins atomically; the other is a no-op and the connector is called once. `test_expired_grant_cannot_be_revoked` pins this.
- **Duplicate requests.** Rejected before the policy runs, pointing at the existing grant or pending review (decision 10). A returned request does not block a resubmission.
- **The model returns garbage.** Both model calls are parsed defensively. Unparseable step 1 output is a failed validation (fail closed, no second call). Unparseable step 2/3 output is DENY at LOW confidence with a risk flag, which routes to a human. An API error is treated the same way. The provider never raises; the router would route to a human if it did.
- **Service restarts with grants outstanding.** State is in the SQLite file. A new process pointed at the same file sees the same grants; `is_active` is computed from `expires_at` so it is correct before any sweep; the approval service and the sweeper both reconcile at start.

## Known gaps and fail-open windows

- **The sweep interval.** `is_active` says false the instant `expires_at` passes, but the external token is only torn down when a sweep runs. Between the two the token is live. This is the one remaining fail-open window, bounded by the sweep interval (five seconds in compose, thirty by default). Closing it fully means the external system enforcing the expiry itself (a token TTL set at issue time), which a real connector should do.
- **First-match ACL.** If a role has two rules whose patterns both match a resource, the first in file order wins. There is no most-specific or most-permissive resolution. The file documents this; it is a limitation, not a design.
- **Mock heuristics are illustrative.** The mock triage step is a placeholder list, a length floor, a keyword check for mutation verbs, and two scope thresholds. It exercises the real recommend-and-defer behaviour but should not be mistaken for a classifier.
- **No authentication on the approval page.** The single-use token is the only credential, and the reviewer's name is a text field. The self-approval check is therefore honour-based. Behind SSO the identity comes from the session and the check becomes real.
- **SQLite single-writer.** Fine for this scale and it is what makes the transitions atomic; it is not a multi-node deployment story.
- **Notifications.** The approval URL is printed to the terminal. Nothing sends it anywhere.
- **Requester history is a first slice.** New requester plus large scope, and recent denial or revocation, route to a human. Per-requester baselines, anomaly detection, agent-vs-human requesters, cool-downs, and counting escalations are listed as TODO in the module and are rules on top of an existing read model.

## Time spent and what is left

Roughly six hours of building, in stages: a walking skeleton (broker, database, mock connector, always-approve policy, six end-to-end tests), the HTTP integration (sidecar, protected service, compose), then the ACL, triage, router, human review, approval page, duplicates, request status, the return-to-requester path, and requester history. Around 200 tests pass under plain `pytest`; the compose run drives the integration subset against real containers.

Left, in the order I would do it: notification and escalation of pending reviews (decision 8), a real connector against the existing two-method interface with the external system enforcing TTL, SSO on the approval page, richer requester-history rules, a REST API for the broker itself, and metrics, in particular how often a reviewer disagrees with the AI's recommendation, which is the number that says whether the confidence threshold is right.
